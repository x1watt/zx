Every archive is a database.

zx: versioned, searchable and verifiable archives, in pure Dart.

zx keeps every version of your files: updates are appended, earlier states stay readable by date, and identical data is stored once. Any file is found in microseconds by SHA-256 or by similarity, and a SQL database lives inside the archive next to the files. Versions can be signed with NOSTR keys, so anyone can verify who wrote them and that nothing changed since, and a README inside the archive describes its contents. Compression goes well beyond the usual formats when there is time for it: built on the context mixing models of paq8px and cmix, zcm level 9 makes a 6.8 MB mixed corpus 33% smaller than xz -9e and 7z PPMd (1.71 MB against 2.57 and 2.55 MB), with 39 to 40% saved on source code and executables and 43 to 46% on photographs and audio, at a few KB/s; level 1 runs at 1.1 MB/s. And it still reads and writes every 7z, zip, rar and tar you have. Pure Dart: a library, a command line and a file explorer for desktop and Android.

Overview

zx also reads and writes the established formats (7z, zip, RAR5, tar and the compressed tars, zpaq) and reads older RAR versions, disk images and firmware. Its LZMA, LZMA2 and PPMd coders are ported from the public domain LZMA SDK and produce output byte-identical to the reference implementation. The library is pure Dart, with no FFI and no native libraries, so the same code runs as the command line program, as a library in Dart and Flutter applications, and in the desktop and Android app.

The .zx format in detail:

  • Generations. Updates are appended and earlier bytes are never rewritten, as in zpaq. Any earlier state can be read back by number or by date; content-defined deduplication stores identical chunks once across files and generations.
  • An embedded database. SQL in the SQLite dialect, key-value stores and time series are stored in the archive itself, versioned with it.
  • Content lookup. Each file carries its SHA-256 and a TLSH digest, so exact and approximate matches are index lookups.
  • Context mixing compression (zcm), from the models of zpaq, paq8px and cmix, with deterministic arithmetic.
  • Optional signed generations with NOSTR keys, checkable without the archive's password.

The test suite compares results against the reference tools wherever they exist: 7z, xz, zip and unzip, tar, gzip, bzip2, rar and unrar, arj, lhasa, zpaq, zpaqfranz, sqlite3, mksquashfs, xorriso, the mkfs tools and paq8px.

The .zx format

A .zx file is a header, a sequence of blocks, and an index with a footer; each update appends further blocks, a new index and a new footer. Every block names the codec chain that produced it, and the file states the oldest version of zx that can decode it, so new codecs do not require a new format and an older reader refuses a file it can not read instead of misreading it. The complete specification is docs/zx-format.md.

Generations
Earlier bytes are never rewritten. A reader opens the last valid footer, so an update interrupted by a crash leaves the previous generation intact. Any generation can be listed or extracted; -mcompact reclaims space.
Deduplication
Content-defined chunks (64 KiB average) are stored once across files and generations. A second version of a source tree added to an archive of the first costs 0.31 MB instead of 4.76 MB; the chunk index of a 100 GiB archive needs 13 MB of memory.
Parallel coding
Blocks are coded by worker isolates within a memory budget, with output identical to the single-threaded coder: 2.9 times faster on 4 threads than on one (LZMA2 level 5, 40 MB of C sources in 2 MiB blocks).
Content hashes
SHA-256 per file in a sorted table, verified on extraction and test, and a TLSH digest per file for similarity search.
Encryption
AES-256-CTR with HMAC-SHA-256 per block (encrypt then MAC), keys from scrypt; file names and sizes are encrypted by default.
Volumes
Volumes of different sizes over several folders or disks, with budgets or until a disk is full; earlier volumes are not needed to append.
READMEs
A README.md in the archive, or in one of its folders, is shown by the app as the description of that folder. Images and linked files must be entries of the archive; links to external sites are permitted, fetching external resources is not (zx readme -check reports violations).

Compression: zcm

zcm is a family of context mixing compressors built from the models of zpaq, paq8px and cmix: data type detection per block (text, x86 code, images including headerless raw ones, audio), an English dictionary transform, word, match, sparse, image and audio models, two-layer mixers with SSE stages, PPMd and DMC predictors gated by measured gain, and cmix's LSTM byte mixer at the top level. The arithmetic is deterministic, so every machine decodes the same bytes. -m0=zcm:auto selects the strongest level that fits a given time and memory budget on the machine at hand.

Database: zxdb

A .zx archive can hold a database next to its files: SQL tables in the SQLite dialect (cross-checked against sqlite3 by differential fuzzing), key-value stores with expiry, partitioned time series and full-text search. Pages are compressed with the archive's codecs. Each commit is a generation of the archive, so every table can be read as of an earlier commit (AS OF '2026-09-01'). Read-only system tables expose the archive's files, generations and similarity search to SQL.

SELECT path, size FROM zx_files WHERE sha256 = x'9f86d081...';
SELECT path, distance FROM similar('photos/IMG_0042.jpg', 20);
SELECT * FROM zx_files AS OF '2026-09-01';

CREATE TABLE notes (id INTEGER PRIMARY KEY, body TEXT) WITH (compression = 'max');
CREATE KV STORE settings WITH (ttl = '30d');
CREATE TIMESERIES logs (ts DATETIME, level TEXT, msg TEXT)
  PARTITION BY DAY RETENTION '400d';

Signed generations

Whoever holds a file can modify it; signing can not prevent that, but it can make any modification detectable. When sealing is enabled, each generation of a .zx archive ends with a seal: a SHA-256 over the stored bytes of the generation and over its index, chained to the seal of the previous generation and signed with a NOSTR key (BIP-340 Schnorr over secp256k1). Because the hashes cover the stored bytes, the seals of an encrypted archive can be verified without its password.

The seal also carries the archive's roles: one admin and any number of maintainers, identified by their npubs and readable by anyone. The admin adds and removes maintainers, decides whether they may sign, and can transfer the admin role to a new key, which must countersign its acceptance. A reader replays the role history offline and checks each generation against the roles in force when it was written; generations signed by a maintainer before their removal remain valid.

zx a -msign=@admin.nsec book.zx chapters/          # new archive; the key becomes the admin
zx seal -sign=@admin.nsec -add=npub1... book.zx     # add a maintainer
zx u -msign=@maintainer.nsec book.zx chapters/     # an update signed by the maintainer
zx seal -full book.zx                              # verify every byte and every signature

A modified byte, a forged generation, a removed seal, a signature by a key that may not sign and an unauthorized change of roles are all reported. Two limits are inherent to any scheme of this kind: the verification establishes which npub signed, not who controls it; and a truncated copy that ends at an earlier, validly sealed generation can only be recognized against an independent record of the latest one. Sealing is optional, can be enabled on an existing archive, and has no effect on archives that do not use it. Keys are passed as a file or through the ZX_NSEC environment variable, not on the command line.

Desktop and Android application

zx-gui is a file manager built with Flutter on the same library. It opens archives, nested archives, disk images and firmware as folders: copying out extracts, pasting in adds. For .zx archives it lists the generations, shows the archive's README, provides a view of the embedded database (tables, key-value stores, time series, queries, file metadata, similarity search) and reports the state of the seals. All archive work runs in background isolates.

On Linux it registers file associations and an "Extract to folder" entry for Nautilus and Thunar; on Android it supports the system's storage access, SD and USB volumes, opening from and sharing to other applications. Details: docs/app.md.
